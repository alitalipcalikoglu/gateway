# CORS

Browser-facing routes declare the origins that may call them. The gateway answers preflights itself, so upstreams never see `OPTIONS` noise and need no CORS logic.

## Route

```json
{ "id": "media-user", "pathPrefix": "/api/media/", "…": "…", "cors": ["https://shop.example.com", "https://admin.example.com"] }
```

`"cors": ["*"]` allows any origin (without credentials). Omit `cors` for routes that browsers never call cross-origin.

## Preflight

```bash
curl -si -X OPTIONS $GW/api/media/v1/files \
  -H 'Origin: https://shop.example.com' -H 'Access-Control-Request-Method: PUT' -H 'Access-Control-Request-Headers: authorization, x-file-name'
```

```
HTTP/1.1 204 No Content
access-control-allow-origin: https://shop.example.com
vary: Origin
access-control-allow-methods: GET, HEAD, POST, PUT, PATCH, DELETE     ← or the route's "methods" list
access-control-allow-headers: authorization, x-file-name              ← echoes the request
access-control-max-age: 600
access-control-expose-headers: Content-Length, Content-Range, Accept-Ranges, ETag, Location, X-Request-Id, X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After
```

An origin not on the list gets `204` with **no** `access-control-*` headers; the browser blocks the call.

## Actual request

Allowed origins receive `access-control-allow-origin` (and `vary: Origin`) on the proxied response as well, including error responses generated by the gateway (401, 429, 413), so the page can read them.

## Routes without `cors`

`OPTIONS` is treated like any other method: forwarded if allowed by `methods`, otherwise `405`. Nothing is added to responses.

## Credentials

The gateway never sets `access-control-allow-credentials`. Send tokens in the `Authorization` header, not cookies, for cross-origin calls.
